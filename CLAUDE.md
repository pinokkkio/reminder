# CLAUDE.md

## Ветки и деплой

* `master` — основная ветка. Это прод: из неё GitHub Actions ([`deploy.yml`](.github/workflows/deploy.yml)) деплоит бота в Telegram Serverless. Агенты и любые другие участники не пушат и не мержат в неё напрямую — только через pull request, который принимает и мержит владелец репозитория.
* Всегда, для любой задачи без исключений: создаём отдельную ветку и открываем из неё pull request в `master`. Работа не ведётся в `master` и не остаётся в локальной ветке без PR.
* Имя ветки — всегда `feature/<название-отражающее-задачу>`: читаемое, на латинице, в kebab-case, коротко и по делу, отражает суть изменений. Примеры: `feature/hero-section-redesign`, `feature/fix-mobile-nav`, `feature/add-contact-form`. Автосгенерированные имена (вроде `claude/random-words-abc123`) не используем — если агент стартовал на такой ветке, переименовываем её в `feature/...` перед пушем.
* PR открывается из ветки в `master` сразу после того, как изменения закоммичены и запушены; в заголовке PR — суть задачи, в описании — что и зачем изменено. Мержит PR владелец репозитория.
* Исключение: самый первый коммит с текущим состоянием проекта был запушен в `master` напрямую по прямому указанию владельца, одноразово, чтобы было с чего стартовать. Дальше правило выше действует без исключений.

## Проект

Telegram-бот напоминаний с мини-приложением на [Telegram Serverless](https://core.telegram.org/bots/serverless) (CLI `tgcloud`). Подробности — в [README.md](README.md).

* `tgcloud/` — всё, что выполняется на платформе: `schema.js` (таблицы), `handlers/` (апдейты Bot API), `endpoints/` (API мини-приложения и служебные `tick`, `setup`), `lib/` (логика).
* `web/index.html` — мини-приложение, одна страница без сборки.
* `scripts/` — проверки и шаги CI/CD; `test/` — тесты (vitest) с фейковым `sdk` на `node:sqlite`.

## Перед коммитом

```bash
npm run verify   # правила рантайма платформы + тесты
```

## Правила рантайма (проверяет `npm run check`)

* В модулях `tgcloud/` импорты — только `sdk`, `sdk/db` и т. п. или относительные пути с `.js`. npm-пакетов, `process`, `require`, `node:` и файловой системы в рантайме нет.
* Все вызовы `db` асинхронные — всегда `await`. Внешних ключей нет.
* Схема меняется только добавлением. Удаление колонок или таблиц — отдельным PR, через `.deprecated()`, когда старый код уже не нужен: CD останавливается на опасных миграциях.
* Встроенного cron у платформы нет: напоминания рассылает `endpoints/tick`, который каждые 5 минут запускает [`tick.yml`](.github/workflows/tick.yml), и попутно — любой апдейт или вызов мини-приложения. Не полагайтесь на точное время срабатывания.
* `@tgcloud/cli` закреплён точной версией: `scripts/lib/tgcloud.mjs` использует его внутренние модули.
